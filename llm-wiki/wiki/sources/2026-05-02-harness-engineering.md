## 核心要点

### 1. Harness Engineering 定义
Harness Engineering（工具工程）是围绕 LLM 构建基础设施系统的总称，目的是更好地驾驭模型的能力。其核心理念类比于马的"挽具"——马有力量但需要挽具才能使用，LLM 有能力但需要 Harness 才能给出好的输出。

### 2. LLM 的四大结构性缺陷
- **无状态**：每次对话结束什么都不记得
- **无法操控外部世界**：只能生成文字
- **上下文限制**：不能无限处理信息
- **输出概率性**：同样输入可能产生不同输出

### 3. Harness 四层架构
1. **记忆层** - 用文件系统做持久化，解决无状态问题
2. **执行层** - 赋予 bash/代码运行/浏览器操控/API调用能力
3. **反馈层** - 通过测试/Linter/CI流水线验证输出（核心层）
4. **编排层** - 复杂任务拆解，并行子任务协作

### 4. 代码领域是突破口的原因
不对称性：代码生成是概率性的，但验证是确定性的。编辑器不会因心情放过语法错误，测试不会假装通过。这种确定性让反馈回路完全自动化。

### 5. 四大设计模式
- **渐进式信息披露**：精准入口文档 + 按需加载
- **沙箱隔离**：独立工作区，改坏直接丢弃
- **仓库即真理来源**：规范写进代码仓库
- **机械化执行约束**：架构约束编码进 Linter

### 6. 工程师核心竞争力转变
从"我能写出什么"转向"我能评估什么"，更深层是"我能设计什么样的系统"让正确的代码被可靠生成和验证。

## 视频内容摘要

视频通过马和挽具的比喻引入，解释了为什么 LLM 需要 Harness Engineering。依次介绍了 Harness 的四层架构（记忆层、执行层、反馈层、编排层），分析了为什么代码领域是 Harness 发展最快的场景，最后总结了四大设计模式和工程师在新时代的核心竞争力转变。

## 关键引用

> 模型有能力，不代表它能够去给出一个好的输出。所以 Harness Engineering 就是研究怎么在这个模型外面套一层好的"挽具"，让模型的能力可以被稳定的并且可重复的去驾驭。

> 反馈层解决就是模型输出不可靠的问题。这个是整个 Harness 框架里面最核心的部分。

> 你不需要模型每次都对，你只需要有足够好的验证手段就够了。
